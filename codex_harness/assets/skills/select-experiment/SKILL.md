---
name: select-experiment
description: Choose and evaluate an opt-in SuperCodex experimental method from observed coding-task failures, recorded costs and available learning data.
---

Begin with the task's observed failure and verifier adequacy. Choose one experiment whose mechanism addresses that failure. Keep a cheap baseline and a strong baseline under the same task contract. Do not enable every method together.

Use independent candidate sampling only when checks can distinguish useful solutions; count all candidates in cost. Use read-only specialist teams for separable evidence gathering, with one final implementer. Use recursive calls for nested repository questions with explicit call, depth and time limits. Model agreement is not an acceptance test.

Fit routing from matched single-model runs including failures. Treat scores as uncalibrated and re-evaluate when repository, tools or model versions change. Retrieve only relevant verified experience with source revisions; exclude the current task and heldout solutions. Keep advice subordinate to repository evidence.

For repeated task families, compare ACE or GEPA candidates on untouched tasks after development optimization. Include reflection and evaluation spend. Training a local LoRA adapter additionally needs curated data and downstream coding evaluations; validation loss alone is insufficient. Preserve experiment artifacts and unknown costs. Prefer the simpler measured policy when gains are indistinguishable.
