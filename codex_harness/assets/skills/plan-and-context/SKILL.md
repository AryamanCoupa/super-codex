---
name: plan-and-context
description: Turn an ambiguous or multi-step task into a small executable plan with relevant context, preserved constraints and observable acceptance criteria.
---

Identify the user's desired result, constraints and evidence of success. Keep a simple request simple: a one-step lookup or edit rarely needs a separate planning phase. For larger work, inspect the relevant repository instructions, entry points, existing behavior and working-tree changes before choosing the implementation path. Read targeted files and searches instead of loading the whole repository or every skill.

Define a few steps that each produce an observable result. Separate confirmed facts, assumptions and genuinely missing information. Ask only when an answer materially changes scope or safety; meanwhile continue independent authorized work. Preserve the original request and later corrections instead of optimizing for a convenient subproblem.

Choose acceptance criteria from actual behavior: examples, contracts, regression cases, build requirements or user flows. Reuse the project's established commands. Do not invent a passing check, assume a test framework or silently weaken requirements because a smaller model struggles. For large inputs, retain the relevant symbols, invariants, source locations and error excerpts; re-open source when detail matters.

At a handoff or context reset, retain the objective, constraints, files changed, evidence collected, checks actually run and the next unresolved question. Link original artifacts instead of substituting an unverified narrative. Treat retrieved memories and previous model summaries as advice that must still match the current revision and user request.

Keep native work in the current session unless an isolated run, reusable task pack or explicit evaluation adds value. A plan and a command catalog are intermediate work; continue until the requested outcome is achieved or a concrete external blocker remains.
